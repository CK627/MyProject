# case12：TCP 重组一致性与 HTTP 响应体精确雕刻

**类型**：流重组保真（提取文件哈希必须与真实文件一致）
**样本**：`2026-10-01-traffic-analysis-exercise.pcap`（HTTP 下载 EXE，官方公布 SHA-256）

## 现象：文件"提取到了"，但哈希不对

扫描该抓包 `--extract` 后成功提取出一个 1.6 MB 的 `.exe`（来自 `x.x.x.x:9000 -> 客户端:63723`
的 HTTP 响应），本地 `shasum -a 256` 与官方答案给出的 SHA-256 **不一致**：

```
本地提取:  dcd1d375...  （错误）
官方答案:  b789adce70c028a6d17be45ec34667aa95586350ee0c4057e75b138b1ad35061
```

"能提出来但内容不对"比"提不出来"更危险——后续所有基于哈希的溯源（VT / IOC 比对）全都错。

## 诊断过程（两层问题，都要修）

### 问题 1：按包序直接拼接，重传/异常分段会污染字节

对下载流做序列号分析：

```
带载荷段: 1219        唯一 seq: 1217（有 1 个完全重复段）
异常点：
  seq=...963 len=6      ← 全零短段
  seq=...963 len=1356   ← 同 seq 的真实 HTTP 响应头（与上面冲突！）
  空洞：...962→...963（1 字节）、...969→...2740319（1350 字节）
```

**根因**：按捕获顺序把每段 payload 首尾相接（naive concat），遇到
①重传段会**重复字节**；②同 seq 的"短段+长段"（采集端异常分段）会**错位**；
③乱序靠后到会**打断文件**。→ 拼接出的字节流与接收端实际收到的字节流不同。

### 问题 2：雕刻边界吃掉流尾填充

修复拼接后重试：文件哈希仍不符。检查发现雕刻从 `MZ` 一直取到流尾，
而该 HTTP 响应头部写明 `Content-Length: 1646592`，实际取到 **1646598**（多 6 字节流尾零填充）。

**根因**：`carve_files` 对"流里最后一个 PE"取到 blob 末尾；blob = 整个会话流，
含响应之间的连读字节与流尾填充。→ 必须**按 HTTP 分帧精确切分响应体**再雕刻。

## 修复方案（已工具化）

1. **`capture.merge_stream(segs)`**：带序号的流按 TCP seq **逐字节 last-wins 覆盖**合并——
   重传/重叠自动去重、乱序按逻辑位置落座、流尾多余字节不进文件；无序号时退化为旧拼接。
   所有消费流的模块（scanner / session / ad / http）统一改走该函数。
2. **scanner 提取阶段"逐响应体雕刻"**：HTTP 响应流先经 `parse_http_responses`
   切分（Content-Length 精确切片 / chunked 自动解码），对每个响应体单独雕刻——
   修正边界为"文件真实结束位置"，不再让流尾/连读字节混入。

## 验证（与官方逐字节一致）

```
[提取] ..._003.exe (1646592 B)   ← HTTP响应体1 (偏移 0)
shasum -a 256: b789adce70c028a6d17be45ec34667aa95586350ee0c4057e75b138b1ad35061  ✓（与官方一致）
```

## 经验规则（后续同类必查）

- **提取到的文件凡涉及哈希/大小比对，先核对三件事**：①流是否有重传/空洞；
  ②文件是否恰好等于 Content-Length；③官方给出的哈希是对"落盘文件"还是"传输流"（一般落盘）。
- 判断"拼接是否正确"的快速方法：从 MZ 开始的 `Content-Length` 字节的 SHA-256
  与官方/IOC 比对——**这是端到端正确性的黄金标准**。
- 恶意的 PE 下载常用"非常规端口 + 裸 HTTP"（如 `:9000`），响应可能伴随
  同 seq 异常短段（采集伪影）——不能假设"一个包 = 一段连续数据"。
