## 识别特征

- 流量里 HTTP 传输内容含 **zip 包**（`misc1_037.zip`），解压得到一个 `ce.txt`
- `ce.txt` 内容是 **98457 行数值**（每行 3 个 0-255 数值）——即 98457 个 RGB 像素

## 分析步骤（含关键陷阱）

### 1. 提取 → 解压 → 拿到像素数据

```bash
ctfsweep misc1.pcapng --extract --extract-dir /tmp/out
# /tmp/out/ 中出现 misc1_037.zip → unzip 得 ce.txt（98457 行 R G B 值）
```

### 2. ⚠️ 核心陷阱：图像宽度是第一优先级

**错误做法**：随手拿常见宽度（如 110）渲染——得到"文字斜排/波浪"的假象，
误认为是手写体、波浪基线、旋转存储，浪费大量时间做各种旋转/镜像变换。

**正确做法**：先做**因子分解**！

```
98457 = 3 × 37 × 887   → 候选宽度：37 / 111 / 887 / 2661
```

**为什么宽度差 1 像素会造成斜排假象**：
设真实宽度 W=111，若用 W'=110 渲染，第 r 行的起点偏移为 r×110，
而它应处的真实位置是 r×111 —— 每行内容"提前"了 r 个像素，
即**每行向左错位 1 像素**。累积 111 行后错位达 111 像素（整整一个屏幕宽），
视觉上就是一道 45° 斜排——**这不是数据特点，纯粹是渲染错误**。

### 3. 判定正确宽度（自动检测）

用 `pixels_to_png.py --auto`：对所有因子候选宽度打分——
- **列错位漂移**（相邻行黑色像素重心的平均位移）：正确宽度 → 文字竖直，漂移小
- **笔画横向连通性**（黑色像素 run 的均方长度）：正确宽度 → 笔画连贯，run 长

实测评分：`W=111 → 6.34`（选中），W=37 → 1.16，W=887 → 0.12。

### 4. 还原后的方向修正

W=111 渲染出的是**竖排 + 镜像 + 倒置**的文字（存储时做了 rotate+flip）。
四步变换取正位：

```
原图(111×887, 竖排)
 → CCW 90°（变 887×111，仍倒置）
 → 180°（文字转正但左右镜像）
 → 水平镜像 flip（完全可读）
组合后 = 逆时针 90° + 180° + 镜像；等价于：先 flip 再 rot90cw 的其他组合均可
```

还原后直读：**`flag{Rgb_dhskjadyhjksndjsagh}`**（前缀 "Rgb_" 呼应 RGB 主题）。

## 解码规则（工具化）

1. **像素总数先做因子分解**——候选宽度只从因子中选（可分性检验）
2. 多候选用"漂移 + 连通性"双指标打分，**渲染 top3 供人工确认**
3. 文字方向不对时穷举 8 个方向变体（4 旋转 × 镜像），逐个看图
4. 已沉淀工具：`lab/tools/pixels_to_png.py`（`--auto` / `--rot90cw` / `--rot90ccw` / `--flip` / `--rotate`）

## 同类变体判断指引

- 行数 × 列数 = 像素总数，**先除再看**（拒绝拍脑袋设宽度）
- 数据里 RGB 全为 0/255 或双色 → 二值图（文字/图案）；连续渐变 → 照片（找隐写或细节）
- 图像还原后若"看起来是文字但读不出"，按 8 方向穷举，不要过度解读"手写体"

## 误报教训（重要）

- 曾一度认为"手写体 + 波浪基线不可机读"——**实际是宽度错位 + 方向未修正**
- 遇到"斜排文字"，第一反应应该是**校验宽度因子**，而不是上旋转工具穷举
