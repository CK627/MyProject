# 第二章：系统总体设计与架构

这一章我主要讲讲这个平台是怎么搭起来的。从用了什么技术、整体架构长什么样，到几个核心机制是怎么设计的，以及数据库里到底存了哪些表。把这些说清楚了，后面第三章讲具体功能是怎么实现的就好理解了。

## 2.1 技术栈概览

在开发这个平台的时候，我选择了目前业界比较主流的“前后端分离”模式。简单来说，就是写页面的归写页面，写接口的归写接口，两边互不干扰，只要约定好怎么传数据就行。

前端这块，我用了 React 配合 Next.js 框架。Next.js 的路由做得很方便，而且自带的服务端渲染（SSR）能让网页打开得更快一点。为了少写点低级的 Bug，我强制要求整个项目都用 TypeScript 来写，虽然一开始定义类型有点繁琐，但到了后期重构代码的时候简直是救命稻草。写样式的话，我没用传统的 CSS，而是用了 Tailwind CSS，这种把样式拆成一个个原子类名的做法，写起响应式页面来特别顺手。

后端这边，我选了 Python 的 FastAPI 框架。顾名思义，它最大的特点就是“快”，而且天生支持异步编程（async/await），用来处理高并发的请求非常合适。最让我喜欢的是它能自动生成接口文档（Swagger UI），这在前后端联调的时候省了我大把的时间。数据库操作我没有手写 SQL，而是用了 SQLAlchemy 这个 ORM 框架，这样在开发的时候我可以用轻量级的 SQLite，以后如果想部署到服务器上，改个配置就能连上 MySQL，代码一行都不用动。

另外，考虑到校园互助里经常需要私聊，我没有用普通的 HTTP 请求，而是直接上了 WebSocket，做了一个全双工的实时通讯模块。至于登录验证，我用的是 JWT（JSON Web Token）方案，用户登录后发个 Token 存在浏览器里，以后每次请求带上这个 Token 就行，后端不需要存 Session，特别适合前后端分离的架构。

## 2.2 系统架构设计

### 2.2.1 整体架构

整个系统就是经典的 B/S（浏览器/服务器）架构。用户只要有个浏览器，不管是电脑还是手机都能访问。

前端服务跑在 3000 端口，主要负责把页面画出来，处理用户的点击操作，然后把数据打包发给后端。后端服务跑在 8000 端口，它就像个大管家，接收前端发来的请求，验证一下身份，去数据库里查数据或者写数据，最后把结果按约定好的 JSON 格式扔回给前端。至于最底层的数据库，目前为了开发方便就用一个 `.db` 文件（SQLite）存着。如果是实时聊天的消息，就不走普通的 HTTP 接口了，而是走 WebSocket 通道直接推送到前端。

### 2.2.2 项目目录结构

代码如果全堆在一起，以后稍微改点东西就得牵一发而动全身。所以我把前端和后端的代码分得很清楚。

前端代码里，页面路由放在一个文件夹，那些能反复用的按钮、弹窗等 UI 抽取成了公共组件，调用后端接口的逻辑也单独封装成了一个工具库。后端代码则是按业务模块来分的，比如处理用户的放在 `users.py`，处理任务的放在 `tasks.py`。除了路由，后端还单独分出了数据库模型定义、输入数据校验（Schemas）以及专门管理 WebSocket 连接的类。我在项目根目录下还写了几个脚本，平时开发的时候一键就能把前后端同时跑起来。

## 2.3 关键机制设计

### 2.3.1 基于WebSocket的实时通讯

在校园互助里，发单人和接单人肯定得商量细节。如果用传统的 HTTP 轮询（比如每隔两秒去问一次服务器有没有新消息），既浪费服务器资源，消息还有延迟。所以我决定直接用 WebSocket。

用户一登录，浏览器就会和后端建立一个长连接。我自己在后端写了个 `ConnectionManager` 类来管这些连接。它把用户的 ID 当作钥匙，把连接存起来。最棒的是，我把它设计成了支持“多端登录”的模式。也就是说，如果你同时在电脑和手机上登录了平台，有人给你发消息，你的电脑和手机会同时“叮”地一声收到提醒，这体验跟微信是一样的。

### 2.3.2 信誉系统与社区治理

怎么防止大家在平台上乱发广告或者接单了又跑路？这是我设计这个平台时想得最多的问题。我最后想出来的办法是：引入“信誉分”。

每个新注册的用户都有 60 分的初始分。你顺利完成一次互助任务，或者别人给你点了赞，系统就给你加分。但如果你在校园墙上乱骂人，被大家投票把评论删了，系统就会扣你的分。
更有意思的是社区治理这块。我没打算自己天天盯着后台当管理员删帖。我设计了一个“拉踩”功能，如果一条评论被很多人踩，踩的比例超过了一个阈值，系统就会自动把这条评论隐藏掉，顺便扣发言人的信誉分。如果你的信誉分攒到了 98 分以上，系统还会自动提拔你当“审核员”，你的一票能顶普通人的好几票。这就形成了一个大家自己管理自己的自治社区。

### 2.3.3 任务悬赏冻结与自动结算

在互助任务里，钱的事最容易扯皮。为了彻底解决这个问题，我设计了一套“先冻结、后结算”的流程。

当你在平台上发一个代拿快递的悬赏任务（比如悬赏 5 块钱）时，系统会先看你虚拟钱包里有没有 5 块钱。如果有，这 5 块钱就会立马从“可用余额”变成“冻结资金”。这时候你这钱是取不出来的。等别人帮你把快递拿到了，你在系统里点一下“确认完成”，系统就会自动把这冻结的 5 块钱划到对方的钱包里。如果你中途把任务取消了，这钱也会原路退回给你。整个过程都是系统自动跑的，谁也别想赖账。

## 2.4 数据库核心表设计

### 2.4.1 实体关系与核心表

整个数据库的设计其实就是围绕着“人、钱、帖子、任务、消息”这五个东西转的。最核心的肯定是“用户表（users）”，每个用户还会对应一张“档案表（user_profiles）”来存信誉分，以及一张“钱包表（wallets）”来存钱，这三张表是一对一绑定的。用户可以在校园墙上发“帖子（posts）”，帖子下面有“评论（post_comments）”，这是一对多的关系。用户还可以发“互助任务（help_tasks）”，一个任务可能会有好几个人来申请，所以任务和“申请记录（task_applications）”也是一对多。最后，用户的钱包里只要钱变动了（比如发任务冻结了钱，或者做任务赚了钱），都会在“交易流水表（transactions）”里记一笔账，保证每一分钱都能查到去向。
