# 第四章：平台测试与运行效果

代码写完只是第一步，到底能不能用、好不好用，还得拉出来遛遛。这一章我主要记录了整个系统是怎么做测试的，跑在不同设备上效果怎么样，以及那些核心功能到底有没有达到我当初设想的目标。

## 4.1 我用什么环境测的？（测试环境）

为了保证平台不是只能在我的电脑上跑，我专门找了不同系统和设备来做测试。

硬件方面，主要开发和测试都是在我那台 i5 处理器、8G 内存的 Windows 电脑上搞定的；为了看看跨系统有没有坑，我还借了同学的 M1 芯片 MacBook 测试了一下。考虑到大家平时肯定是用手机上这个平台多一点，我又分别用自己的 iPhone（iOS 17）和另一台安卓手机测试了移动端的排版和操作。

软件环境上，前端跑的是 Node.js（18.x版本），后端用的是 Python（3.9版本）。浏览器测试我主要用的是平时大家最爱用的 Google Chrome，顺便也拿 Edge、Firefox 和苹果自带的 Safari 跑了一圈，看看排版有没有错位。

## 4.2 各个功能模块测试

在功能测试这块，我没搞那些虚的，主要就是自己模拟各种正常和“手滑”的操作，看看系统能不能扛得住。在登录注册测试中，正常注册和登录肯定没问题，我故意输错了几次密码，或者用已经注册过的邮箱再注册一次，系统都能弹出正确的错误提示，为了测试 JWT Token，我故意把 Token 删了或者等它过期，系统立刻就把我踢回了登录页，这块的安全拦截做得还算到位。在校园墙测试中，发帖、点赞、评论这些基础操作都很流畅，我重点测了那个“匿名发布”功能，确实看不出是谁发的；另外，我还专门找了几个同学的账号一起给一条评论点“踩”，踩的次数一到设定的阈值，那条评论真的就自动隐藏了，发评论那个号的信誉分也被扣了，这说明社区自治的逻辑是通的。在悬赏任务测试中，这块是核心，主要测钱算得对不对，我试着在钱包没钱的时候去发一个悬赏任务，系统直接提示余额不足，拦住了我，充了钱再发任务，发出去的瞬间，钱包里的钱就冻结了，任务做完或者中途取消，钱的流转也一分不差。在实时聊天测试中，我把网页同时开在电脑和手机上，用另一个账号发消息过来，电脑和手机几乎是同时收到的，这说明 WebSocket 的多端同步做得很成功，顺便也测了下加好友和拉黑功能，拉黑之后对方发消息确实被拦截了。

## 4.3 把整个流程串起来跑一遍

光测单个模块不行，我模拟了一个最真实的校园互助场景，把整个流程从头到尾串了一遍。首先，我用账号 A 充了 100 块钱，然后发了一个代拿快递的任务，悬赏 10 块钱，这时候 A 的可用余额变成了 90，冻结了 10 块。接着，我换账号 B 登录，去大厅看到了这个任务，点了一下申请接单。切回账号 A，看到 B 的信誉分挺高，就同意了让他接单，这时候任务状态变成了“进行中”，B 终于能看到原本隐藏的快递取件码了。然后，B 拿到快递交给了 A，A 在系统里点击“确认完成”。这时候重头戏来了：系统自动把 A 冻结的那 10 块钱解冻，并且打到了 B 的钱包里，B 的余额多了 10 块。最后 A 和 B 互相打了个五星好评，两个人的信誉分都涨了。整个测试下来，流程非常顺滑，钱和状态的变更完全符合我当初的设计预期，没有出现卡壳或者算错钱的情况。

## 4.4 浏览器兼容性测试

现在的浏览器内核五花八门，为了防止出现“在 Chrome 里好看，在 Safari 里排版全乱”的情况，我把主流浏览器都测了一遍。结果还不错，前端用了 Tailwind CSS 写响应式布局，加上 React 的底子，不管是在 Chrome、Edge 还是 Safari 里，页面都没变形，底层的 WebSocket 聊天也没有因为浏览器不同而断线。

## 4.5 运行效果总结

经过这么几轮的折腾，这个“智慧校园服务平台”算是立住了。

七大核心功能全都能正常跑，尤其是那个“先冻结后打钱”的任务大厅，算账算得很明白，没出过乱子。手写的那个 WebSocket 聊天模块也挺给力，消息收发基本感觉不到延迟。最让我满意的是，因为一开始就坚持做了响应式设计，现在用手机浏览器打开这个平台，界面看起来就像个原生的 App 一样，整体体验非常不错。
